# InferSim

[![ci](https://github.com/Nags-gk/infersim/actions/workflows/ci.yml/badge.svg)](https://github.com/Nags-gk/infersim/actions/workflows/ci.yml)

**Live dashboard: https://nags-gk.github.io/infersim/** (the Python package runs in your browser via Pyodide)

A performance model for LLM inference on GPUs, LPUs and heterogeneous systems. Every layer of a
Hugging Face model becomes operators with FLOPs and bytes; each operator is timed on a roofline;
a serving simulator and a design space sweep turn that into the numbers inference teams argue
about: time to first token, time per output token, tokens/s per user and tokens/s per device.

The core package is pure Python with no dependencies, so the same code runs in CI, from the
command line, and live on the dashboard.

## What it models

| Area | Details |
|---|---|
| Architectures | Dense GQA (Llama-3.1 8B/70B/405B, Qwen2.5), mixture of experts (Mixtral 8x7B, DeepSeek-V3 with expected active experts per batch), multi-head latent attention (DeepSeek-V3, weight-absorbed decode). Loaded from `config.json`; parameter counts tested against published sizes. |
| Operators | Every linear layer as a GEMM (M, N, K) per tensor-parallel rank with tile padding; prefill attention (causal, flash-style) and decode attention over the KV cache; norms and activations; embedding and LM head. |
| Hardware | T4, A100, H100, H200, B200, GroqChip v1 and the Groq 3 LPU. Each spec lists its source; every estimated figure is listed as an assumption. |
| GPU layouts | Tensor, pipeline and expert parallelism; all-reduce takes the faster of ring and one-shot; all-to-all for expert dispatch and combine. |
| LPU layouts | All weights in on-chip SRAM across many chips; layer pipeline across chips; ops wider than one chip split and all-reduced; KV cache must fit on chip too. |
| Heterogeneous | Disaggregated serving (GPU prefill, LPU decode, KV cache shipped over 400 Gb/s) and an attention/FFN split (attention and KV on GPUs, FFN weights on LPUs). Both labeled speculative. |
| Serving | Discrete-event simulator: Poisson arrivals, continuous batching, chunked prefill, KV-capacity admission, p50/p99 TTFT and TPOT. |
| Design space | Sweeps layouts x precision x batch, keeps the Pareto frontier of tokens/s per user vs tokens/s per device, and picks the best layout under an interactivity SLA. |
| Calibration | Fits compute efficiency, memory efficiency and launch overhead to measured latencies with Nelder-Mead, reporting MAPE on a held-out split. |

## Findings (modeled)

Generated by `bench/run_bench.py`, also shown on the dashboard.

- **Decode is memory-bound until batch ~257 on H100.** Llama-3.1-8B's FFN GEMMs cross the
  roofline ridge at the same batch in BF16 and FP8: FP8 halves the weight bytes and doubles peak
  FLOPs, so the ridge moves with it.
- **25% of 70B single-user decode on 8x H100 is fixed cost:** kernel launches (18%) and 160
  latency-bound all-reduces per token (7%) do not shrink with more tensor parallelism.
- **LPU vs GPU, Llama-3.1-70B:** 197 Groq 3 LPUs reach about 6.6x the per-user speed of the
  fastest GPU layout, at about 12x lower throughput per chip. At a 50 tok/s/user SLA the best
  layout swept is 2x B200, TP2, FP8.
- **MLA caches 7.3x less KV per token** than Llama-3.1-405B's GQA (34 vs 252 KiB/token in FP8).
- **Weights alone need 157 Groq 3 LPUs for a 70B model in FP8,** before any KV cache.

The LPU numbers rest on assumed compute and link figures (listed in `infersim/hardware.py`).

## How the numbers are made

For each operator, time = max(compute, memory) + launch overhead, where compute is tile-padded
FLOPs at `eff_compute` x peak and memory is bytes moved at `eff_memory` x bandwidth. Collectives
use an alpha-beta model. Tests check that no operator beats its ideal roofline time.

**Not yet measured.** All latencies are modeled. The efficiency knobs are defaults, not fitted.
Calibration against a real GPU (a T4, with `torch.profiler`) is the next milestone; the fitter and
its holdout evaluation are already in `infersim/calibrate.py` and tested on synthetic data. Use the
absolute numbers as estimates and the comparisons between layouts as the point.

## Run it

```bash
pip install -e ".[dev]"
pytest -q                                   # 49 tests, about 1 s
infersim step --model llama-3.1-70b --hw h100 --tp 8 --batch 32
infersim roofline --model llama-3.1-8b --hw h100 --phase prefill --tokens 4096
infersim dse --model deepseek-v3 --sla 50
infersim serve --model llama-3.1-8b --hw h100 --rate 12 --requests 300
infersim calibrate measurements.csv --hw t4   # columns: model,phase,batch,tokens,measured_s
python bench/run_bench.py                   # regenerate site/data/results.json
```

Python API:

```python
from infersim.system import GPUDeployment
from infersim.ops import StepShape

dep = GPUDeployment("llama-3.1-70b", "h100", tp=8, precision="fp8")
print(dep.step(StepShape.decode(batch=32, ctx=4096)).bottleneck())
```

## Layout

```
infersim/
  models.py      architectures from config.json, parameter and KV accounting
  hardware.py    device catalog with sources and assumptions
  ops.py         one step -> operators (GEMMs, attention, collectives)
  roofline.py    operator timing, ring / one-shot all-reduce, all-to-all
  system.py      GPU, LPU, disaggregated and attention/FFN-split deployments
  serving.py     continuous-batching discrete-event simulator
  dse.py         sweeps, Pareto frontier, best layout under an SLA
  calibrate.py   Nelder-Mead fit of efficiencies to measurements, MAPE
  web.py         JSON views for the dashboard
site/            dashboard (static HTML/JS + Pyodide worker)
tests/           pytest + Hypothesis property tests
.claude/         Claude Code skills and a hook that runs the guardrail tests on every edit
```

## Built with coding agents

Developed with Claude Code. `CLAUDE.md` and the skills in `.claude/skills/` tell an agent how to add
hardware or models; a PostToolUse hook runs the catalog, model and roofline tests after every edit,
so an agent cannot add a device without a source or a model whose parameter count is off.

## Limitations

- No measured calibration yet (see above). Launch overhead dominates some low-batch GPU results
  and is the parameter most likely to move after calibration.
- Communication does not overlap with compute; real stacks hide some of it.
- MoE experts are assumed load-balanced; no expert imbalance or token dropping.
- LPU and heterogeneous models use assumed compute, link bandwidth and latency.
- No speculative decoding, quantization error, or KV-cache offload.
